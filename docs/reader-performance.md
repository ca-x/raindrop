# 阅读器加载与阅读体验优化

本次针对大量订阅下的重复读取、刷新历史查询，以及文章队列失败后的恢复进行优化。用户截图中的“无法载入文章队列”属于读取已存文章的 API 失败，与订阅源的抓取状态是两个独立流程。

## 实现

- 最近刷新状态通过现有 `idx_refresh_runs_feed(feed_id, queued_at, id)` 索引取第一条记录，不再对每个源的全部历史做窗口排序。不改数据库结构，保留时间相同按 ID 排序、无刷新记录、多用户隔离与分页语义。
- 连续实时通知在首轮快速响应后，每 5 秒最多启动一轮订阅和队列校准；保留最后一次通知。后台读取不与前台请求并发抢占，页面隐藏、离线和卸载时停止调度。
- 实时连接正常但读取失败时，也会每分钟尝试恢复。没有当前来源快照时使用完整首批替换，保留下一页游标；已有列表继续采用不打乱阅读位置的待合并更新。
- 文章列表 GET 遇到网络错误或 HTTP 500/502/503/504 时，等待 750 毫秒补一次请求。切换来源会取消等待；401/403/429、无效响应与修改状态操作不重试。
- 设置界面按需下载，失败仅显示局部恢复提示。备份的目标、计划、历史只在进入备份设置时读取。
- 文章接口错误记录安全分类 `pool_acquire`、`database`、`projection`、`content` 或 `validation` 与耗时。日志不包含用户标识、搜索词、订阅地址或底层数据库报错正文。

## 阅读界面

保留现有暖纸色、墨蓝色控件和正文衬线字体。正常刷新状态收敛到来源栏底部，可展开查看完整时间；快捷键说明通过队列菜单展开；重新载入按钮使用刷新图标。首次队列失败显示独立中文恢复入口，已有内容时保留列表并使用轻量警告。订阅名称保持单行，完整名称保留在提示中；刷新状态图标不再被误套上未读计数的背景。

- [FreshRSS 的阅读视图](https://freshrss.github.io/FreshRSS/en/users/03_Main_view.html)：清晰区分来源导航、未读状态、文章标题与阅读视图。

## 验证与适用范围

本地 SQLite 对照实验使用 50 个源、每个源 8,640 条刷新历史（每 5 分钟一次，约一个月），重复 7 次取中位数。仅“取最近刷新记录”查询从 **344.307 ms** 降至 **0.055 ms**，结果逐条一致；执行计划从历史物化与临时排序改为覆盖索引查找。这不是端到端启动耗时，也不是用户部署环境的测量。

实时调度回归用 20 秒内 100 次通知模拟持续刷新：旧实现执行 100 轮读取，新实现窗口内不超过 5 轮，且保留末尾校准。另有连接正常时的失败恢复、轮询与通知重叠、首次失败恢复分页、取消重试及最多一次重试的测试。

验证命令：

```sh
npm --prefix web run typecheck
npm --prefix web run check:reader-types
npm --prefix web run test:ci
npm --prefix web run build
cargo fmt --all -- --check
cargo test --locked --test feed_subscription_contracts --test feed_query_contracts --test reader_api
```

浏览器验证使用隔离 SQLite 数据库与 12 个源、1,152 条未读的本地示例内容，覆盖列表、正文、失败重试、设置入口和窄屏溢出。SQLite API 与查询测试通过；PostgreSQL/MySQL 的集成用例在未提供测试数据库 URL 时跳过。

截图本身不能区分数据库连接池等待、查询执行或投影数据错误。若部署后仍失败，查看 `Reader entry list failed` 日志的 `failure_kind` 和 `elapsed_ms`，结合 `/api/v1/entries` 的状态码继续定位；不能把本次优化视为对未知现场故障的根因证明。
